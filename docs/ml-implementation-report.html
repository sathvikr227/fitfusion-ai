Three of the reference guide's targets were met; two were not, and this report says which and why.

01How the five models work together

Two entry points use the layer. Plan generation is seeded by the recommender; the weekly check-in runs the full pipeline, where each model's output becomes the next one's input and the RL agent makes the final call.

The weekly check-in reads the user's week once, through a shared builder in lib/ml-service/history.ts. That single read produces the completion rate, sleep average, streak, last four sessions, and injury features. Both the replan route and the analytics readout consume it, so the dashboard can never disagree with the decision that was actually made.

The injury classifier runs first and flags any muscle group scoring above 0.7. The Transformer then classifies the last four sessions as REGRESS, PLATEAU or IMPROVE. Both outputs enter the RL state vector [completion, sleep/10, injury_flag, trajectory/2, min(streak,14)/14], and the PPO agent returns REDUCE, MAINTAIN or INCREASE.

That action becomes the directive in the LLaMA prompt — and then, critically, it is applied again deterministically after the model responds. The ±15% delta is scaled into sets and projected burn, exercises loading flagged muscle groups are stripped by name, and the emptiest remaining workout day is converted to rest. The LLM shapes the plan; it does not get to decide whether the safety rules were followed.

02What was implemented, per model

Each model trains from a reproducible script, saves a versioned artifact, and is served by its own endpoint so a failure in one never takes down the others.

01

Calorie burn predictor

XGBRegressor · 200 trees · depth 6 · lr 0.1 + SHAP
MAE87.9 kcal
RMSE113.8
R²0.845
MET baseline MAE416.9 kcal
Target < 25 kcalnot met

Trained on all 973 rows with the documented six features, StandardScaler, and an 80/20 split. A TreeExplainer is built once at startup, so every prediction returns its top-5 SHAP contributions in kcal — the workout log surfaces these as a diverging bar chart headed "Why 412 kcal?".

The model cuts error against the MET table it replaces by 79%, but 87.9 kcal is well above the guide's 25 kcal target. The dataset's calorie values average 905 with a standard deviation of 273, so a 25 kcal MAE would mean explaining 99% of the variance from six coarse features. Avg_BPM would close most of the remaining gap, and it is deliberately not in the documented feature list.

02

Hybrid diet + workout recommender

StandardScaler + cosine similarity, top-10 neighbours + content filters
Precision@30.747
Precision@20.511
Precision@10.219
Coverage1.000
Diversity2.99 / 3

The collaborative half finds the ten most similar users in the 973-row cohort and ranks their workout types by share. The content half filters that ranking against active injuries, then selects foods from the 7,385-item nutrition index by goal. Output is injected into the LLaMA prompt as an explicit data-grounded recommendation seed before generation.

Precision@3 of 0.747 clears the guide's 70% target. Precision@5 as written is not reportable: the dataset has only four workout classes, so a top-5 list would trivially score 1.0. Leave-one-out Precision@1–3 across all 973 users is reported instead.

Two correctness problems surfaced during testing and were fixed. Ranking weight-loss picks by lowest calories returned diet soda, black coffee and tea, so nutrition floors now apply. More seriously, a keyword blocklist leaked animal foods into vegetarian results — Seal, Whale, Sea Cucumber, then Ling and Orange Roughy. Vegetarian and vegan now run an allow-list matched against the food's leading identity, so an unrecognised food is dropped rather than served.

03

Multi-label injury risk classifier

MultiOutputClassifier(XGBClassifier) · 100 trees · depth 4
Knee F11.000
Back F10.947
Hamstring F11.000
Shoulder F10.286
Macro F10.808

Four proxy labels for knee, lower back, shoulder and hamstring, built from the documented biomechanical thresholds. Per-label scale_pos_weight handles the imbalance (positives run 4.7–10.6%). Scores above 0.7 drive rest-day insertion and exercise removal, and every response carries the "not a clinical diagnosis" disclaimer.

The documented knee rule matches zero rows. Resting_BPM > 80 AND Workout_Frequency > 5 is unsatisfiable on this dataset — resting BPM tops out at 74 and frequency at 5. The trainer detects the degenerate rule and substitutes a quantile-calibrated form of the same two signals (BPM > 68, the 75th percentile, and frequency ≥ 4), recording the substitution in both the artifact and the report.

Shoulder is not identifiable from the documented features. Its label keys on Workout_Type == Strength, which the guide's feature list excludes. An ablation confirms the diagnosis rather than asserting it: adding Workout_Type lifts shoulder F1 from 0.286 to 1.000. The shipped model keeps the documented features.

04

Transformer progression predictor

nn.TransformerEncoder · d_model 32 · 4 heads · 2 layers · 20 epochs
Accuracy0.460
Macro F10.438
MLP baseline0.427
GBM ceiling0.400
Majority class0.389

Exactly the specified architecture, with a learned positional embedding added so ordering reaches attention. 925 sequences of shape (4, 4) built as pseudo-sequences grouped by experience level and workout type, Gaussian augmentation at std 0.05, CrossEntropyLoss and Adam at 1e-3.

Accuracy of 0.460 misses the 65% target. The evidence says this is the data, not the model: a gradient-boosted tree on the same flattened windows reaches only 0.400, below the Transformer, and the majority class is 0.389. The Gym Members dataset is cross-sectional — it has no completion rate and no calendar — so the "sessions" in a pseudo-sequence are unrelated rows and carry almost no temporal signal to learn. The Transformer still beats every baseline tried.

Two of the four session features are constructed, and the report records this: completion rate is a proxy (duration over the group's 90th percentile) and day-of-week is synthetic. At inference the model receives real FitFusion values for all four.

05

PPO adaptive replan agent

stable-baselines3 PPO · MlpPolicy · 100,000 timesteps
PPO reward3.771
Rule-based reward3.878
PPO injuries/ep0.668
Rule injuries/ep0.780
No-trajectory ablation3.738

FitFusionEnv implements the documented 5-dimensional Box state, Discrete(3) action space and reward function (+1 improvement, −2 injury, −0.5 churn), calibrated from real pilot data: mean completion 0.857 and standard deviation 0.246 across 14 user-days, and an active-injury rate of 0.105 across 19 profiles.

A naive simulator would make REDUCE trivially dominant, since cutting the plan always raises the share of sessions completed. The environment therefore models training adaptation — a latent ability that grows under productive overload and decays under chronic undertraining — so reducing forever erodes the ability that produces future completion.

PPO does not beat the rule baseline on mean reward (3.771 against 3.878 over 500 episodes on identical seeds). It does cut injury events by 14% and churn slightly. The learned policy is REDUCE-heavy at 86.7%, which is a direct consequence of the documented reward paying for completion improvement. Removing trajectory from the state costs 0.033 reward, so the Transformer input helps, marginally.

08Database changes

One additive migration. No table was altered destructively and no existing column changed type. 

-- web/supabase/migrations/20260909_ml_audit_columns.sql
alter table workout_plans
  add column if not exists injury_risk jsonb,
  add column if not exists ml_meta     jsonb;

create index if not exists workout_plans_user_created_idx
  on workout_plans(user_id, created_at desc);

injury_risk stores the per-muscle-group scores that drove a replan; ml_meta stores the whole decision record — completion rate, sleep average, streak, trajectory class, RL action and state, removed exercises and the rest day inserted.

The migration is optional to run immediately. The replan route inserts with the audit columns and, if they do not exist, retries without them and logs a warning. The same payload is always written inside plan.ml_meta either way, so nothing breaks and no data is lost while the migration is pending.

A schema bug found and fixed

/api/adaptive-replan was selecting sleep_logs.duration_hours. That column exists in the migration file but not on the live table, which only has sleep_hours — the column every other screen reads and writes. The select was erroring, so average sleep had been permanently null in the replan prompt. It now reads sleep_hours, and sleep genuinely reaches the RL state.

10Training instructions

Both Kaggle datasets download from the public endpoint with no credentials, cached automatically on first run. Nothing needs collecting by hand. 

# from ml-service/ — one-time setup
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt

# optional but recommended: calibrate the RL environment on real data
.venv/Scripts/python.exe -m training.export_pilot_data

# build order — later models assume earlier artifacts exist
.venv/Scripts/python.exe -m training.train_calorie      # ~10 s
.venv/Scripts/python.exe -m training.train_recommender  # ~30 s
.venv/Scripts/python.exe -m training.train_injury       # ~15 s
.venv/Scripts/python.exe -m training.train_transformer  # ~2 min
.venv/Scripts/python.exe -m training.train_rl_agent     # ~25 min

Use Python 3.11 or 3.12. Torch and XGBoost wheels do not yet exist for 3.13+, which is why this session built against 3.12 rather than the 3.14 on your PATH.

Each script writes its real metrics to models/reports/<model>.json, including any target it failed to hit. None of the five needs a GPU: the Transformer is two layers at d_model 32, and PPO is bound by the environment step, so a GPU runtime makes it no faster. The scripts are plain modules, so a Colab cell only needs the repo plus pip install -r requirements.txt.

The real-data run

Executed against pilot user 048f4f3b — age 22, BMI 27.1, goal weight loss, real average sleep 7.39 h, real completion 0.83, and one active left-hamstring injury recorded in the injuries table. The layer responded coherently end to end:

  • Calories — 598.9 kcal for a 45-minute strength session at 86 kg, against a 322.5 kcal MET baseline, with resting BPM correctly reported as imputed.
  • Recommender — Cardio / Strength / Yoga, with HIIT excluded because of the hamstring injury, and a calorie-deficit diet matching the weight-loss goal.
  • Injury risk — hamstring 0.99 and flagged; knee, back and shoulder all 0.001. The one muscle group the user is actually injured in is the one the model flagged.
  • Trajectory — REGRESS at 0.725 confidence, consistent with the completion dip to 0.4 inside the four-session window.
  • RL agent — REDUCE at 0.81 confidence, given injury flag 1 and a regressing trajectory.

Bugs found by testing and fixed

  • Vegetarian results contained fish and marine mammals. Blocklists kept leaking; switched vegetarian and vegan to an allow-list matched on the food's leading identity.
  • Weight-loss diets were diet soda and black coffee. Nutrition floors added, so picks now carry real protein.
  • Resting a whole day discarded healthy exercises. The rest day now lands on the emptiest remaining day rather than the one that had the most flagged work.
  • An out-of-range weekly frequency dropped calls to fallback. Clamped at the caller.
  • Average sleep was silently always null — the sleep_hours column fix above.

12Limitations and unresolved issues

  • The pilot dataset is far smaller than the guide assumes. The document describes 12 users and 46 plans. The live database has 19 profiles but only 2 users with any workout history — 18 logs, 17 sleep records, 3 injuries, and 14 user-days of completion data yielding 9 usable 4-session windows. That is enough to calibrate the RL environment but not to train or validate on FitFusion's own data, so models 1–4 are trained entirely on the Kaggle datasets.
  • Resting BPM is never observed. vitals_logs is empty, so both the calorie and injury models impute it from the training median. Every response lists what was imputed. The wiring to read real values is in place and will pick them up the moment users start logging vitals.
  • Shoulder risk is effectively non-functional at F1 0.286, for the identifiability reason above. It is still returned and still counted, so a false shoulder flag can strip pressing work. Adding Workout_Type to the feature list would fix it, at the cost of deviating from the documented spec — worth raising before doing.
  • The RL agent does not beat the rule baseline on reward. The documented reward pays +1 whenever completion improves, and reducing intensity is the most reliable way to make that happen, which is why the learned policy is 86.7% REDUCE. Adding an explicit progression term to the reward — rewarding sustained ability growth, not just week-over-week completion — is the change most likely to make the agent clearly better than thresholds.
  • Transformer accuracy is capped by the dataset. 0.460 against a 0.400 GBM ceiling on the same features. Real improvement needs real sequential data, which the app will accumulate as users log sessions.
  • Not tested through a browser login. The Next.js routes were verified via their auth guards, the live round trip, direct model calls on real user data, and the orchestration unit checks. Driving the actual signed-in UI would have required authenticating as a user, which I did not do.
  • The muscle-group keyword list is duplicated across app/features.py and lib/ml-service/injury-rules.ts, because the service scores risk but never sees the plan while Next.js edits the plan but never scores risk. Both files carry a comment to keep them in sync.

REQUIRED · 02

Deploy the ML service and set its environment

Where
Render dashboard, then Vercel project settings
What
